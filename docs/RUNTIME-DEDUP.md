# One runtime: reconciling the editor's runtime copy with Runtime/

The editor (`Sandbox.exe`) carried a private copy of the game runtime inside `SandboxApp` (split across `sandbox/src/Sandbox*.cpp`), and the standalone `AverEngineRuntime.exe` runs its own copy from `Runtime/`. The goal ("Phase C") is ONE runtime: the editor calls the `Runtime/` library for each subsystem and deletes its copy, with **the editor's behaviour as the reference**, the library still linking no ImGui, and editor-only needs entering through explicit hooks. Method: land the runtime-only fixes first (they cannot move a pixel in `Sandbox.exe` while the editor does not link `Aver.Runtime.Game`), add hook plumbing whose defaults reproduce today's runtime exactly, then switch editor code to the library one subsystem per commit, each with a before/after comparison of the SAME project in both hosts (`scripts/verify-game.ps1`'s divergence gate, screenshots, and the `[Occlusion]` / `[LOD-*]` log counts where the render walk is involved). Once `SandboxApp` itself calls the library, GAME-LIFT.md's "no commit can move a pixel in Sandbox.exe" guarantee no longer holds by construction (it depended on never editing `sandbox/**`); each editor-side swap needs its own gate run, run by the user per the standing rule.

The reconcile maps behind this were produced by four read-only readers at `385a5e8e`; function names are the durable locators, line numbers drift. `docs/GAME-LIFT.md` is marked HISTORY (an earlier AverGame.exe state, paths that no longer exist): do not take its line numbers or function bodies as current truth; only its two surviving traps (`xformPoint`'s reversed-argument twin, the file-static-promotion warning) still generalise.

## Settled decisions (2026-09-19; reasons kept)

- **The editor was fixed, not the runtime, for PHYSICS/AUDIO apply.** The editor applied `PHYSICS.GRAVITY/FIXEDSTEP` and `AUDIO.*` only from inside `applyProjectRenderSettings`, so they needed a RENDER.* key and an attached Voxi; a project stating only `PHYSICS.GRAVITY` had it silently ignored. Gravity and audio mix have nothing to do with Voxi, and the runtime was already right, so "the editor is the reference" did not apply. Both now run from `SandboxApp::applyProject`, outside every Voxi and `hasRenderSettings()` gate, at the position the runtime uses (`applyProjectPhysicsSettings` / `applyProjectAudioSettings` take `fmt::ProjectDesc`; physics is internally gated on `aver_phys_ready()`; every `audio_abi.h` setter is a documented no-op before `aver_audio_init()` succeeds). Side effect: in a build with `AVER_MODULE_VOXI` off these keys were discarded entirely before and now apply. Landed as its own commit so it can be reviewed or reverted independently.
- **The runtime gates AI/graph ticking on "PLAYING, or no GameMode was declared".** The old justification for being ungated was that a graph-only project never reaches `aver_fw_begin_play` because there is no C# GameMode. **That premise was stale:** a graph class parented to "GameMode" gets the GAME_MODE bit through `sealClass`'s inherited kind flags, so `aver_fw_find_class_with_flags` finds it. Verified against the packaged runtime on graph-only PTTest, which logs `[Graph] GameMode 'AN_FPRules' begins play` and `[Game] play session begun automatically (GameMode class 10)`. The ungated tick was mutating worlds that had not begun play. The second term keeps the one case the old premise protected: a project declaring no GameMode in any language. **Measured when the editor's equivalent was ungated:** on PTTest over 1000 frames with Play never pressed, a class-placed graph's own VAR climbed from 3.6e-05 to 12.31s across 4003 tick lines. Synapse AI (`agentSystem`/`perceptionSystem`/`btSystem`) was fully ungated in Runtime (editor: gated on PLAYING or the `--spawn-test` term); it is now gated on `aver_fw_play_state() == AVER_FW_PLAY_PLAYING`. Anim ticks unconditionally in both hosts (deliberate asymmetry, copied from the editor).
- **Sky defaults with no SKY record: the editor moved to the format's.** The editor's mirror read (0.19,0.42,0.78)/(0.72,0.80,0.90) while the runtime (`GameApp.hpp:420`), the format (`OcWorld.hpp:401`) and `rhi::SkyAtmosphere` itself (`RHI.hpp:253`) all read (0.24,0.45,0.85)/(0.72,0.83,0.95); the editor was the odd one out of three, so it cannot be the reference for a value the file format declares. `SandboxApp.hpp` now holds the format's numbers. **This moves pixels in the editor** for a level with no SKY record under the AUTHORED sky model (`--sky-authored`, the Sky panel's dropdown, or a level that authored `skyPhysical=false` and nothing else): `applyLevelEnv` is guarded on `w.hasSky` (`LevelSky.hpp:56`) and the frame loop copies the editor's mirror over `sky_` every frame. Under the default Physical model the dome fit overwrites both in the frame constants (`D3D12Device.cpp:4211`, `VulkanDevice.cpp:2356`, both gated on `model == Physical`) and the authored numbers are inert, which is how the wrong dome went unnoticed.
- **`--cam-wobble` during Play: the difference is kept, deliberately.** It shows in the runtime and is overwritten by the play camera in the editor. The flag exists to make a still frame move for verification, nothing combines it with a play camera, and the runtime applies its offset only to the view matrix because it has no movement yaw to corrupt (the editor mutates `yaw_` itself from a latched `camWobbleBaseYaw_`, so wobble steers WASD; the runtime restores `yaw_` immediately, "nowhere safe to accumulate drift"). Unifying would be churn on a flag no shipped path uses.
- **The manifest gained a post-process channel.** `RENDER.EXPOSURE`, `RENDER.BLOOM`, `RENDER.AUTOEXPOSURE` and `RENDER.TONEMAP` reach `rhi::PostSettings` in both hosts, on the pattern `RENDER.RESTIRHISTORY` established. Each has a "not stated" sentinel so an absent key leaves the compiled default alone: negative rather than zero, because a bloom intensity of exactly 0 is a legal authored value meaning "no bloom pass at all", and `FormatTest` pins that round trip. An explicit `--exposure`/`--bloom` on the command line still outranks the manifest, the precedence an earlier defect inverted.
- **A backgrounded game no longer receives input.** `publishInput`'s `focused` argument was `e.window() != nullptr` ("a window exists", not "has focus"). The Win32 foreground test the mouse-capture block already computed is now hoisted and passed instead. `publishInput` publishes an explicit release for every slot when unfocused, so nothing can latch. A bounded `--frames` run deliberately keeps the old answer: a capture's window is opened unactivated, so a real foreground query would report "not foreground" for the whole run and turn every gate's input into releases. Off Win32 the old answer stands (no portable foreground query).
- **`RENDER.GIVOLUME` is honoured.** The editor auto-fits the GI volume only when `project_.giExtent <= 0.0f`; Runtime called `fitGiVolumeToLevel()` unconditionally, so an authored volume was silently discarded (the editor's own comment, `SandboxLevelLoad.cpp:1182-1189`, measured on PTTest: a real 5659 cm authored half-extent shrank to a fitted 2356 cm). Now `if (project_.giExtent <= 0.0f) fitGiVolumeToLevel();` (`GameApp.cpp`).
- **Dead-handle rung fixed by construction (C7 step 1).** R's `drawWorld` used to read `content.authoredFor(mat)` and, if non-zero, take the authored branch with no liveness test, so a stale handle came out as pure white metal. `drawWorld` now calls the shared `resolveSurfaceLook`, which requires `authored && authoredLive` and otherwise falls through; the shared header's test already pinned that fall-through, which is why the editor never had the bug. It was unreachable in the shipped host (`GameApp::openProject` runs once per process) but mattered because the editor, which reloads, calls the same walk.

## Reference findings still load-bearing

### C1/C2: content index, resolvers, mesh registry, materials

- `GameContent` carries `meshParts_`, `resolveMaterialGraph`, and the asset-resolving logic shared with the editor. **Why multi-material draws split per part:** ray tracing/BLAS constraints force per-part splitting rather than a per-geometry material index (`SandboxApp.hpp:1658-1668`). The editor's comment (`SandboxAssets.cpp:790-798`) found it via "Importing 53 foliage meshes... 37 of them name exactly one material", i.e. ~16/53 in that set (any bark+leaves tree or multi-slot palm) would visibly regress if the runtime's mesh registry were used unsplit.
- **Materials load lazily per surface through `materialForSurface`, Binaries-first, by design** (`GameContent.hpp:79-84`: the runtime carried a copy of the editor's eager loader, nothing called it, it was removed). Level-load material binding is already unified through `world::instantiate`'s `opt.bindMaterial`. `materialForSurface`'s 3-candidate path array (`Binaries\Materials\<n>.ocmat`, `Content\Materials\<n>.ocmat`, `Content\<n>`) is duplicated with the editor's `MaterialResolve.hpp` on purpose (it must stay includable from a headless test with no `Aver.Pbr` link); parse failure `break`s rather than falling through, and negative results are cached.
- **`releaseProjectMeshes`:** the editor's original version destroyed `meshParts_`/cluster-cut handles but never the base `sceneMeshes_[id]` handle (and never erased `meshBounds_`/`meshPathById_`), leaking one GPU mesh per non-split asset on every project reload. `GameContent::releaseProjectMeshes(device, destroyBaseHandles = true)` now exists (the editor passes `false` for its own bookkeeping, `SandboxAssets.cpp:421`); any new caller must destroy the base handles too. The runtime calls it never today (one `openProject` per process).
- **Depth proxy:** the editor builds the FULL LOD ladder (`MeshLodLadder`, `--lod-select`); the runtime computes and uploads exactly ONE depth-only proxy level (`depthProxyMap_`), because "the game has no runtime LOD selection at all... uploading the rest of the ladder would be VRAM that nothing can ever look up". Deliberate.
- **GPU cluster/LOD path is editor-only and big:** `ensureLodMeshPipeline` (`#if AVER_MODULE_SCENE && AVER_MODULE_TRIFACTOR`, D3D12-only, caps `meshShaderTier>0 && shaderModel>=65 && dxcAvailable`) builds an AS/MS/PS mesh-shader pipeline (`cluster_material.hlsl`) merging Voxi's GI/shadow register map into table 0 (contract documented in `SandboxAssets.cpp`), so huge meshes (the doc's example: a 17.18M-triangle tree) draw through GPU clusters. Zero occurrences under `Runtime/`; `Aver.Trifactor` is already linked there, so it is an unported feature, not a structural block. Own slice ("GPU virtualized geometry for the packaged runtime").
- **Voxi attach:** both hosts run the same sequence; the two adjacent lines `textureFactory_ = device->resources(); voxiRenderer_.materials().setTextureResolver(&resolveMaterialTexture, self);` are load-bearing (they make `resolveMaterialTexture`'s `!textureFactory_` null-check unreachable). The runtime attaches Voxi in `onInit` BEFORE `openProject`, so `attachVoxi` does its own standalone manifest re-read into a local `fmt::ProjectDesc seed` (it needs some manifest to size the voxel volume even for `--frames`-only runs with no project); `openProject`'s later `applyProjectRenderSettings()` re-derives identically from the real `project_`. Two reads of one file by design, not two sources of truth.
- Editor-only, no lift: `makeMaterialFor(MeshObj&)` and `objects_` (synthetic placeholder scene, `--furnace-grid`); `warnDeadMaterialHandle` diagnostic. `loadProjectParticleEffects` is identical and the runtime's guard is correctly looser (no SCENE needed, CPU-only). Cosmetic: one editor log string in `resolveMaterialTexture` carried a mis-encoded em-dash.
- Guard mismatch worth a hand check: the editor gates `buildMeshParts`/`meshDefaultMaterial` behind `AVER_MODULE_LANDSCAPE` while the call site sits only under `AVER_MODULE_SCENE`, so SCENE=ON/LANDSCAPE=OFF could be a link error or change which fallback applies; not verified whether that combination is ever built.

### C3/C5: project apply, physics, audio, tick groups

- **`applyProjectRenderSettings` is the most bug-scarred function** (its N7 comment records four regressions of the CLI-override precedence). Shape: mirror `projectBackend_`/`frameBudgetMs_`/`averSrProjectDefault_` unconditionally; early-return on `!hasRenderSettings()`; defer on `!voxiAttached_` via `projectRenderPending_`; re-seed via `applyProjectVoxiSettings()` (idempotent); **Phase A** commits tier overrides (`--gi/--rt/--pt`) and force-offs (`--no-gi/--no-rt`) alone, then **Phase B** applies every other knob override (`--msaa`, `--rt-rays`, `--rt-render-mode`, `--refraction`, `--rt-shadow-denoise`, `--pt-bounces`, `--layered-bsdf`, `--gi-sky-occlusion-rays/tile`, `--gi-intensity`, `--rt-pixels-per-ray`, `--gi-update-interval`, `--gi-mode`, `--restir-visibility`, `--denoiser`) against the post-Phase-A settings; then the 4-field manifest-contradiction WARN, physics/audio apply, PtSceneView reconciliation. The runtime has only the shared two-phase manifest apply and the contradiction WARN (log text differs: runtime omits `project_.manifestPath`; align when touching).
- **Do not lift the A2 check or PtSceneView:** `PtSceneView.hpp:11` says outright "a reference view, not a render mode", a diagnostic accumulator (`--pt-scene`/editor Quality combo) for validating GI convergence. Runtime's CLI parsing (`GameApp::parseArgs`) carries none of the ~20 override flags.
- **Keep Runtime's ordering; do not import the editor's defer/retry.** The editor needs `projectRenderPending_` only because Voxi attaches after `applyProject` is first called in `onInit`; Runtime calls `attachVoxi` before `openProject`, so its `if (!voxiAttached_) return;` is dead in practice. A future `onInit` reordering could resurrect the need: leave a comment at the call site naming the invariant.
- **Frame-budget controller** (`voxi::frameBudgetTick`): 30-frame warm-up, 250 ms hitch rejection, EMA(0.9/0.1), 15%-band hysteresis (drop immediately, climb only after 60 comfortable frames), 5-rung ladder over `giUpdateInterval`/`giCones`. It runs on a **copy** of `voxi::Renderer::get().settings()` and then `setSettings(vs)`, never writing back to the singleton. The editor runs it in a bounded `--frames` capture only if `--frame-budget` forces it; the runtime has no such capture mode to protect and runs it whenever `cfg_.maxFrames == 0`. Before the lift `RENDER.FRAMEBUDGETMS` was parsed (`OcProject.hpp:121`) and never read by `Runtime/`.
- **Physics init / audio init / tick groups were already at parity:** same "NO IMPLICIT GROUND" rationale; ordering physics init, audio init, project open (level load adds a static body per colliding placement gated on `aver_phys_ready()`); tick order `AVER_FW_TICK_PRE_PHYSICS` -> `aver_phys_step` -> `AVER_FW_TICK_PHYSICS` -> `AVER_FW_TICK_POST_PHYSICS` (the step sits between PRE_PHYSICS and PHYSICS despite an adjacent comment's wording). The editor widens the gate with a `--spawn-test` term, a CLI harness with no place in a game. `aver_audio_collect()` is not gated on Play ("voices outlive a session"). Runtime auto-begins play at boot when a project declares a `[AverGameMode]` subclass (`beginPlayIfGameModeDeclared`: "a shipped game has no editor Play button, so booting it IS beginning play"); the editor's Play is manual. Deliberate.
- Project-open differences that stay: the editor shows `LoadingScreen`, sets Actor/Anim editor content roots, runs the `pendingUpgrade_`/`editor::inspectProject` upgrade flow (a shipped manifest is generated by `stage-game.ps1`), `startContentWatch()`, and sets the window title on every open; the runtime pre-scans the manifest once in `GameApp::config()` because a title must be known before the window exists. The editor declares graph classes inside `applyProject`; the runtime does it in `onInit` after `openProject` (`initScripting`/`discoverProjectGraphs`, then `spawnClassPlacements`). Order (classes declared before class placements spawn) is preserved; keep the runtime's open-vs-script-init split.
- `projectBackend_` and `averSrProjectDefault_` are mirrors with no effect on backend selection (that happens at boot from `--backend`/BootConfig); the shared apply need not accept them.

### C4: level load

- Placement loop, sky/sun/fog/clouds (`assets::applyLevelEnv`, per-field guarded), GI-volume fit math, `unload`, and `spawnClassPlacements` are shared or near-identical. `loadOcworld` "succeeds" on a legacy file's `OCMAP 1` header while silently dropping ROOT/CLIENT/SURFACE/GROUND/KILLZ/DEFORM records, so before the runtime dispatched on `fmt::levelFileIsLegacyOcmap` a shipped game opening a genuinely legacy map (e.g. OpenConstructor's demoworld.ocmap) loaded an incomplete level with no warning. `GameLevel::load` now has the synth-and-translate block (`loadLegacyOcmap`).
- Landscape and water are an always-on part of the editor's `loadLevel` (not toggles); streaming is opt-in even in the editor (Window menu, MCP command, `--chunk-stream N`) and needs a manifest key or CLI flag for a packaged game. A class placement's `snapToGround` needs the landscape seam too (`GameLevel.cpp`, `hooks_.groundHeightAt`); easy to land landscape and forget that caller.
- **Player Start is two things; only one belongs in the library.** The resolved spawn value (position + yaw) is what a shipped game needs; the visible marker entity (cube mesh, Outliner selection, undo, `editor::refreshPlayerStart`) is authoring UX. Do not build a shared "marker" abstraction: the SPAWN record is the shared contract, not an entity. The SPAWN/CAMERA fields live on `OcWorldData`, not the `OcWorldEnv` base `env_ = w` slices to, so they must be captured as plain fields on `GameLevel` the way `env()`/`hasFog()` are. `FrameworkAbi.cpp::aver_fw_begin_play` spawns the default pawn with null transforms (origin); `SceneCensus.hpp:13` states "the game spawns at a PlayerStart". CAMERA-record precedence (`--cam` > level `CAMERA` > `frameCameraOn`) stays editor-only: the shipped camera comes from `drivePlayCamera` reading the possessed pawn.
- The runtime has no engine-default GameMode/Pawn/Controller fallback (`engineDefaultGameMode`, spectator/drone Play): `beginPlayIfGameModeDeclared` logs a warning and the world stays inert. Plausibly correct (an unauthored GameMode is a content bug) but confirm with the design owner. `--open-level` (`openMapPath_`) outranking the project's start map is editor-only.
- **`navPathForLevel` is duplicated** (`Runtime/src/GameApp.cpp:253` and `sandbox/src/NavBakeCommand.cpp`, editor-only header) under different guard macros (`AVER_MODULE_SYNAPSE_SCENE` in Runtime vs `AVER_MODULE_SYNAPSE`, `modules/synapse.scene/CMakeLists.txt:31` vs `modules/synapse/CMakeLists.txt:23`). Pure path manipulation; fold into one definition next to `OcNav.hpp` in Aver.Formats rather than a third copy.
- Net-new library classes are `GameLandscape` (needs `if(TARGET Aver.Landscape)` link; section load, quadtree, ring-tile streaming, Jolt heightfield collision, material/UV-tiling bind via a `bindMaterial`-shaped hook), `GameWater` (needs `Aver.Fluids`; simulated-softbody and analytic Gerstner + buoyancy plane via `aver_phys_set_water_plane`) and `GameStreaming` (`ChunkWorld` per PCGVOLUME field, the densest function in the file). Device-scoped teardown takes `rhi::IDevice*` (nullptr = nothing resident). Sequence them last and verify each with `--frames N` renders and `--scene-census` before wiring `SandboxApp` to call them.

### C6/C7/C8: camera, draw walk, input

- **C6 camera: parity confirmed.** Defaults `camPos_{7,7,4.5}`, `camForward()` (byte-identical), `Mat4::lookAtLH`, `perspectiveLH(radians(60), aspect, 2.0f, 200000.0f)`. Aspect is deliberately different: the editor divides the dockspace central-node rect (`vpW_/vpH_`), the runtime the swapchain. Sky/fog/post push differences that are by design: the editor gates `sky_.enabled` on a Show-menu toggle, applies `--sky-light`/`--sky-authored`/`--sun-elevation` every frame, wraps the sky in `fluids::applyUnderwaterFog` when water is attached, and clears to chrome-grey `(0.055,0.055,0.062,1)` outside the viewport rect vs the runtime's black. The editor's large per-frame Voxi reassert block (`frameBudgetTick`, GI/denoiser/AverSR-auto, five console debug-reset slots) is GI-slice territory.
- **C7 shared walk.** Frustum-plane derivation, `CMeshRenderer` visible-bit check, `!skinned` static-bounds override, world-space AABB cull ("degenerate box is drawn, not culled"), the authored/look/fallback material ladder with once-per-name warnings, skinned-handle substitution (the editor's `posedHandle` also checks `softBodyScene_`), and sticky `setDrawBlended` are the same shape in both. The three correctness bugs the runtime had (culled entities dropped with a bare `continue`, slot-0-only draws, no owner-hide) are fixed in the shared walk. Reaching Voxi's submit from the direct route is a sink on purpose: the library links no path tracer and never will.
- **Editor chrome stays editor-side:** selection outline, PlayerStart billboard icon, grid/nav/collider overlays, gizmo and sculpt cursor (all `drawLines` after the walk), `noEditorChrome_`/`anyPlayActive()`/`maxFrames_` gates, occlusion `showCulled` tint, the `objects_` placeholder pass, capture/gate harnesses, `drawUiDemo`, fluids/water and landscape draw, free-fly camera and its chords, `InputOwnership` arbitration (ImGui `WantCapture*`, drawer/landscape scopes; a pure header with its own headless test).
- **C8 input.** The landed `InputPublishPolicy` carries RESOLVED answers, not the editor's raw conditions (`releasedByUser`, `uiWantsKeyboard`, `uiWantsMouse`), which are an ImGui-shaped question that `InputOwnership.cpp` already answers; passing raw terms across would put a second copy of the arbitration inside an ImGui-free bridge. Fields: `focused` (master switch; false publishes an explicit release into every slot, never an early return), `keyboardToGame`, `mouseToGame`, `gamepadActive` (its own field: a text field steals a keystroke, never a controller button), `captured`/`capturedDx`/`capturedDy`, and `eaten[AVER_FW_KEY_COUNT]` (slots a host chord claims; published as RELEASES, not skipped, since skipping is how a key latches down forever). Mouse capture (Win32 `ClipCursor`/`SetCursorPos`/`ShowCursor`, gated on an active play session; the editor keeps its release chord Shift+F1 / PlayReleaseMouse on top) fixes mouse-look that otherwise hits the window edge and stops (the runtime's deltas are raw `WM_MOUSEMOVE` accumulations, `modules/platform/src/InputState.cpp:64-65`). Editor `startPlay`/`stopPlay` snapshot/restore local transforms and sync physics bodies; the runtime's one-shot boot needs neither.
- `drivePlayCamera`: the runtime handles only PLAYING (no drone/spectator stand-in) and sets no owner-hide state of its own; pawn-follow math (`aver_fw_view`/`aver_fw_view_entity`, first- vs third-person pivot + boom) is byte-identical. Animation curve/notify and Synapse target/perception relays are at parity.
- **HUD design question still open:** how does a project name its default HUD for `scripts_.hudDraw`? Options: (a) a scripts/.cs file with a known method name, (b) a manifest key `RENDER.HUD`, (c) a convention like a "GameHud" class auto-found by the framework. The editor has no convention; a shipped game needs one.

## Shared API patterns established

Reuse these rather than inventing new shapes:
- **Static resolvers + `void* user`** (GameContent model): a library function invokes host-specific logging/allocation without knowing the host; log sinks are function pointers so `[Sandbox]` vs `[Game]` prefixes stay host-specific.
- **Pure-function helpers over `Settings&`** (`ProjectRenderApply.hpp` model; unit-tested in `tests/formats/src/ProjectRenderApplyTest.cpp`): no singleton state, no ImGui, no `AVER_WARN`.
- **Header-only pure utilities** (`FrameBudget.hpp`, CLI-override precedence): portable across the library/sandbox boundary without a second copy drifting.
- **Optional hooks with null = today's behaviour** (`DrawWorldOptions`' callbacks): default-constructed options reproduce the existing walk bit for bit, which is what they are verified against.
- **"Editor only" by non-invocation, not `#ifdef`:** plain extra public methods the runtime never calls, not compile-time branches inside the library. New library classes follow GameContent: `IDevice*`-only interface (no `Engine&`), explicit `if(TARGET ...)` guards on the CMake link, so the library stays headless and both hosts link subsets.

The hosts still differ on: project title resolution; free-fly camera (editor only); `InputOwnership` arbitration; the `--sky-*`/`--sun-elevation` CLI overrides (verification-only, editor-only).

## Risks and what to check (user runs these)

1. **Shadow/GI popping fix:** images change for shipped games with off-screen casters. Load a level with a strong caster near the frustum edge in both hosts; rotate until it leaves; confirm the shadow no longer disappears.
2. **Multi-material split:** screenshot-diff a known multi-slot prop in both hosts (part colours/textures, not just silhouette).
3. **Owner-hide:** possess a first-person pawn; its own body (`kMeshRendererHiddenFromOwner`) must not render forward.
4. **Player Start:** `--open-level <X>` through `AverEngineRuntime.exe` with a GameMode and an authored Player Start (and a SPAWN-only level, no marker); compare spawn position and yaw with editor Play (the managed side seeds `Character.cs` yaw from the placed transform; do not break it).
5. **Mouse capture:** look in one direction for seconds (unbounded rotation); alt-tab away and back mid-look, no single-frame spin (`warpToAnchor`'s foreground guard).
6. **Frame-budget controller:** first time the runtime throttles under load; run a heavy scene with `RENDER.FRAMEBUDGETMS` set, confirm `giUpdateInterval`/`giCones` drop and recover after ~60 comfortable frames, matching an editor Play session.
7. **`PHYSICS.GRAVITY/FIXEDSTEP` in Runtime:** grep demo/test `.ocproject` files for these keys; any project depending on the old always-default behaviour changes. **`RENDER.GIVOLUME`:** compare the `[Voxi] GI volume` log line (centre/extent) between hosts.
8. **Synapse gate:** a no-GameMode project with a Synapse agent must now freeze in the shipped build.
9. **CLI-override collapse** touches the most bug-scarred function: isolated, behaviour-preserving commit, tests that pin Phase A/B ordering, and a gate run on that commit even though no `Sandbox.exe` pixel should move.
10. **Legacy `.ocmap`:** load a genuinely legacy map (ROOT/CLIENT/SURFACE/GROUND/KILLZ/DEFORM) in both hosts; placement counts and `[Level] ... legacy .ocmap` logging must agree (the worst divergence is one that looks like it worked).
11. **Mesh-handle leak:** switch projects several times and watch mesh-resource counts (PIX or an RHI diagnostic; agent gate tools are not to be run).
12. **Scope gap:** LOD/occlusion/Trifactor, and anything else not yet in the shared hook set, can still differ between `Sandbox.exe` Play and `AverEngineRuntime.exe`; do not let "C6/C7/C8 done" read as "the two renderers match".

Separate slice (C9+) with its own measurement/gate discipline since it changes performance and, for LOD, visible geometry at distance.

## Implementation notes for future slices

### When moving the depth-prepass + occlusion walk onto shared drawWorld

The editor's walk order is (1) a depth prepass writing Z only, excluding skinned/translucent/cluster; (2) a colour pass submitting per route. The runtime must not lose the occlusion-pyramid trust gate (`SandboxRender.cpp:480-485`, "if Motion < threshold, trust the pyramid"): a frame with high motion over large draws can invalidate the pyramid and cause false occlusion, and the editor's per-entity motion check prevents that. The selection capture (`SandboxRender.cpp:1540-1568`) sits between LOD logging blocks; whoever moves it to a hook must NOT let the pre-walks stop calling `resolveSurface`/`planEntityDraws` (measured via `[Occlusion]`/`[LOD-SELECT]` log lines before and after).

### When writing the HUD slice

(Landed since; kept for the open naming question.) Wire `Aver.Render.UI` into `GameApp`, register the `UiRenderer` the way `attachVoxi` does, call `aver_ui_begin_frame` in `onUpdate`, call `submitGameUi` from `onRender`.

### When future slices touch SandboxRender.cpp

The file was ~2900 lines with occlusion/LOD/depth-prepass machinery deeply interleaved. Any refactor must preserve (1) per-submesh material resolution inside the entity loop (via `GameContent::meshParts_`), (2) the occlusion-pyramid trust gate, (3) the log-line counts (`[Occlusion]`, `[LOD-SELECT]`, used by gates for regression detection). Verify via before/after capture diffs (screenshots + log line counts) on the same project, run by the user per standing rules.
