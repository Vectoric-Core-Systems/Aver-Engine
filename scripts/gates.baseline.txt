# The oracle's expected raw 8-bit probe codes, one line per (configuration | gate | r,g,b).
#
# Read by scripts/gates.ps1, which is the only thing that should ever write it (-Record). Compare the
# RAW CODES and never the floats: a one-code move hides completely inside %.2f, which is why the
# probe line prints both.
#
# A value here moving is either an announced, understood, oracle-moving change or a regression. There
# is no third case. Whichever it is belongs in the commit message and in docs/STATUS.md.
#
# RE-RECORDED 2026-08-02 by ./scripts/record-gates.ps1 -Only Both, and VERIFIED: 162 gates across
# nine configurations (18 gates x 9, up from 17 x 9), 15 values moved, 9 added, none dropped, and the
# immediate read-back sweep reported ALL GATES PASS.
#
# WHY 15 MOVED, when the tree had not changed since the last Release recording: this file was stale.
# It was last written at 79f6f04, BEFORE the reflection energy correction; gates.baseline.release.txt
# was re-recorded after it at 2d4e1a1 and this one was not carried along. The pair had been torn ever
# since, disagreeing on the 15 RT-affected rows across the five RT-capable configurations. Recording
# only one half is what creates that state, which is why -Only Both is the default and why both files
# belong in the same commit. Release moved 0 values in this same run, which is the confirmation:
# Release was already right, Debug was the stale half.
#
# THE 9 ADDED are rt-penumbra x nine configurations -- the gate added by ae47a2f, which had never
# been recorded and so had been scoring NO-BASELINE (counted as a failure) since it was written.
#
# Verifying straight after recording is the step that makes this trustworthy rather than merely
# written down: numbers measured minutes earlier that then fail to reproduce would be non-determinism,
# not a regression, and this is the one moment that distinction can be established.
#
# Measured on an AMD Radeon RX 7800 XT, driver 32.0.23027.2005. See docs/STATUS.md 4h for what each
# configuration is and why its numbers differ, and 4v for the probe repair below.
#
# THE RELEASE BASELINE IS STILL STALE -- only the Debug tree was recorded. Run
# `./scripts/record-gates.ps1 -Only Release` to close it.
#
# WHY THE PROBES MOVED, since the header above says a moved value is either announced or a regression.
# Both applied, and they had to be separated before either could be believed:
#
#   * The PROBES had gone wrong, and that is not a value change. `0fe81e2` made the level a docked
#     tab and the scene composite into a texture; the viewport went 2750x1711 -> 2750x1639. A
#     relative probe survives a change of SIZE but not of ASPECT, because the projection moves with
#     it -- so shadow/sunlit/penumbra slid onto plain floor and five gates defined to differ all
#     returned 94,102,129. Re-picking them by intent lands `shadow` on 23,40,86 against a recorded
#     22,40,86: the geometry never moved, the probes did.
#   * The CENTRE probe was on the placeholder cube's corner edge, where the 7x7 varies by 83 codes
#     and one pixel decides which face is sampled. gates.ps1 has carried a note saying it must be
#     re-picked rather than re-recorded; this is that being done. `gi-debug` read 156,55,36 from the
#     edge and reads 103,39,30 from the face interior, against a recorded 101,38,31.
#   * What genuinely moved, once the probes were honest, is the GI value on the sun-blind face:
#     75,25,21 -> 92,28,22. That face is lit only by indirect light, and `1b4db02` (the shadowed
#     world ends in a ramp instead of a cliff) and `a743ab0` (dominant-axis projection in the
#     object's frame) are both announced GI changes. Brighter and warmer is what a ramp instead of a
#     cliff looks like on a surface whose entire budget is bounce.
#
# THE NEW PROBES WERE CHECKED FOR REPEATABILITY BEFORE ANY OF THIS WAS WRITTEN DOWN: five consecutive
# runs each of centre / gi / penumbra / sunlit / shadow returned bit-identical codes, 25 runs with zero
# variation. That matters here more than usual, because whole-frame screenshots of this renderer are
# NOT reproducible (~2400 differing bytes run to run). The oracle survives that only because these
# probes sit in flat neighbourhoods -- which is now a stated selection criterion rather than a lucky
# property. That prediction held: the re-record wrote exactly the values those 25 runs produced, and
# the verification sweep reproduced them again immediately. What changed was this file, not what the
# renderer does.
